# 2026-10-02

## chess-rl-bench: project setup and L0 foundation

Built the L0 foundation of `chess-rl-bench`, a benchmark harness for naive RL
approaches to chess. Six levels behind one `Policy` protocol.

### Environment
- `.venv` in repo root. numpy 2.5.3, python-chess 1.11.2, pytest 8.x.
- torch intentionally NOT installed yet; it is an optional extra for L4/L5 only.
- Run tests with `./.venv/Scripts/python.exe -m pytest`.

### Key correction to the original spec
The spec named a "chessboard library" and described an output space of
`(row 8, col 8, piece 5, dir 3-8, size 1-8)`. That space is the vocabulary of
`chessboard` on PyPI (v1.5.4, GPLv2, 2017) -- a CLI solver for *combinatoric
puzzle placements*, not a playable board. It has no move generation, no turns,
no pawns, and raises on any position where pieces attack each other. Confirmed
by reading its source.

Resolution (user confirmed): use **python-chess** as the rules layer and wrap
our own numpy array-board on top. Moves are addressed as
`(from_square, to_square, promotion)` instead of the puzzle tuple.

### Design decisions worth not re-litigating
- **Plane layout**: `(12, 8, 8)` bool for piece planes, array row = rank,
  row 0 = rank 1. Mirrors python-chess square indexing exactly so no flipping
  happens anywhere except at display time.
- **Canonicalisation**: rank reflection + colour-block swap, NOT a 180
  rotation. See below.
- **Move masks factorised as `(64, 64, 5)`**: `[from, to, promo_slot]` with slot
  0 = not-a-promotion and slots 1-4 = N/B/R/Q. Flat action index is
  `(from*64 + to)*5 + slot` over an ACTION_SPACE of 20480.
- **Value planes** (`capture_value`, `danger_value`, `attack_balance`,
  `own_danger`) are OFF by default in `encode()`. They cost ~40x the binary
  planes. Turn on for L2 and inference, off for corpus building.
- **Channel order is load-bearing.** L3 weights and L4 checkpoints index by
  channel number, so appending is fine but reordering silently corrupts saved
  models. `CHANNEL_ORDER_VERSION` / `COLOUR_PAIRED_CHANNELS` in encode.py pin it.

### Bugs found and fixed (all had passing-looking output before)
1. **`canonical` used a 180 rotation.** Mapped d8 -> e1 instead of d1, silently
   transposing queenside and kingside. It looked correct on the symmetric
   opening array, which is why it survived the first round of testing. Now a
   rank reflection (`flip_ranks`).
2. **`canonical` double-rotated the colour blocks** during in-place assignment.
   Now builds the output in one pass with `np.empty_like`.
3. **Value planes were reflected unconditionally.** White-to-move positions had
   their value planes flipped -- the majority of any corpus, so it did not look
   like a bug. Guard is now `canonicalise and board.turn != chess.WHITE`.
4. **Promotion slot overflow.** `PROMO_SLOT[QUEEN]` was 4 in an axis of size 4.
   `NUM_PROMO` is 5 (sentinel + 4 pieces).
5. **King piece-square table not rank-mirrored for Black.** Start position
   evaluated to +50 instead of 0, biasing every search towards White. The king
   is in a separate branch from the other tables, which is how it was missed.
6. **`MidstateStore.sample` over-delivered and could duplicate.** Now samples
   without replacement, capped at `min(n, len(entries))`.
7. `hit_rate`/corpus JSON round-trip `material_ratio` was rounded to 4 places,
   shifting entries across the phase boundary on reload. Now full precision.

### Testing infrastructure that earned its keep
`tests/conftest.py::colour_mirror` is the highest-value helper in the repo. It
swaps colours and reflects ranks, carrying castling rights and the en-passant
target across. Every symmetry bug above was caught by comparing
`encode(position)` against `encode(colour_mirror(position))`. It must stay
correct: an early version dropped castling rights and the en-passant square,
which produced *false* failures that cost real time to diagnose.

### Status
- L0 complete: `bitboard`, `masks`, `cache`, `encode`, `value`, `game`.
- 163 tests passing in 4.6s.
- L1 (blind factored softmax) is next.

## L1 / L1.5 complete: the blind policy, and the finding it produced

New modules: `policy.py` (blind factored softmax + counters),
`train_naive.py` (credit assignment + training loop), `diagnostics.py`.
281 tests passing in 4.9s.

### The L1 headline result, and why it is the benchmark's actual output

**A blind policy under a ply cap cannot learn from win/loss reward.** Measured:
12 self-play games at 60 plies produced 0 decisive results and **0 logit
updates**. After 400 training games, an evaluation match still ended with 55 of
60 games unfinished and the trained policy *losing* the 5 that resolved.

This is not a bug. Verified three ways:
- Random play reaches a decisive/drawn result in only ~1/3 of games at 300
  plies (`reasons: max_plies 13/20`).
- Greedy-material (a *seeing* policy) finishes 100% of games with ~2.5x the
  capture contact rate. The diagnostic can tell the two apart, so it is
  measuring something real.
- Blind play makes contact (`Qxh5+` appears in ordinary games) but essentially
  never delivers mate.

The consequence for the build: **L1 needs shaped reward to train at all.**
`TrainConfig.shaped_reward` (default on) scores an unfinished game by the
static evaluation of its final position instead of discarding it. Same 12
games: **2160 updates with shaping, 0 without.** That is the whole difference.

Two more structural fixes fell out of this:

1. **Self-play against the same live object is degenerate.** Both sides make
   identical decisions, so a symmetric position mirrors itself and one side
   cannot be better than the other. `FactoredSoftmaxTrainer._opponent()` now
   deep-copies a *frozen* snapshot as the opponent, refreshed every 10 games,
   with its own RNG stream. Colours alternate each game so no first-move bias
   is learned.
2. `FactoredSoftmaxTrainer(TrainConfig(...))` now works — passing only a config
   used to be silently treated as the policy and fail far from the call site.

### A property of factorised softmax worth remembering

A factored softmax with zero logits is uniform **per factor**, not uniform over
the move set. `P(from) * P(to|from) * P(promo)` means each origin spreads its
own mass over its own destinations, so a square with more legal moves gives each
of its moves less probability. `uniformity == 1.0` holds *only* when every origin
has the same destination count — true in the opening (ten origins x 2 dests) and
in symmetric middlegames, false otherwise (0.881 and 0.808 on two probe FENs).
Never above 1.0. Documented in `policy_sharpness`.

### Test-suite correction
`test_play_game_reaches_a_real_result` asserted random play always finishes
within 300 plies. That was false in general and became actively wrong once the
expensive claimable-draw scan was removed from `is_game_over` for the 17.6x
speedup (e.g. threefold-repetition games now correctly run to the cap). Split
into `test_play_game_always_terminates_with_a_reported_reason` (asserts a valid
reason, not a finished game) and `test_random_play_finishes_for_at_least_some_games`.

### Status
- L0 + L1 + L1.5 complete. 281 tests, 4.9s.
- `diagnostics.py` (`compare_policies`, `format_comparison`) gives a readable
  side-by-side table and is the seam the L6 tournament will widen.
- L2 (minimax + non-learning wrapper) is next. The trainer already accepts an
  external `opponent=`, which is the hook L2 needs.

## L2 complete: alpha-beta search and the non-learning wrapper

New module `src/chessrl/search.py`: `MinimaxEngine`, `MinimaxPolicy`,
`InformedMinimaxPolicy`, plus `score_move` / `order_moves`.
New test file `tests/test_search.py` (48 tests). **331 tests passing, 102s.**

### What L2 is made of
Negamax + alpha-beta, MVV-LVA ordering, zobrist transposition table, iterative
deepening, quiescence with stand-pat. `chess.polyglot` must be imported
explicitly — `import chess` alone does not expose `chess.polyglot.zobrist_hash`,
which is how cache.py does it too.

Node counts at depth 4 from the opening, as an ablation:
full **2049**, no-TT 3254 (the TT saves 37%), no-iterative-deepening 2665,
no-quiescence 2059. Quiescence is node-neutral here; it exists for correctness
against the horizon effect, not for speed. Worth remembering next time someone
asks whether an optimisation "helped" — the TT and ID clearly did, quiescence
did not, and conflating the three would have hidden that.

### The claim I had to correct
I first documented the wrapper as "cannot change the returned move". That is
**false** and the test caught it. Correct statement: ordering cannot change the
*value* returned by a correct-window alpha-beta, but it decides which move is
returned when several share that value, because the first move to reach alpha is
kept.

Measured, `.../4pP2/8/8/PPPPP1PP/RNBQKBNR b KQkq f6 0 3`: Nf6 and Nc6 both
evaluate to exactly **90** at depth 3. Plain engine returns Nf6 (board order);
the wrapper returns Nc6 because L1's blind prior weights the b8 origin 0.0385 vs
0.0256. It resolved a tie on no chess grounds — which is exactly and only what a
blind prior can legitimately do. Tests now assert the value invariant plus "any
disagreement must be a genuine tie", which is the honest and still-strong
property.

### L2 measured strength
- **Wins 100% against every lower level** — L1 blind, random, greedy-material —
  18/18 across three matches, all decisive, zero unfinished.
- Deeper beats shallower: d2 beats d1 (2-0), d3 beats d2 (2-0, 2 draws).
- Finds Qxf7#, Qh4# and back-rank mates at depth 2, in 0.14s at depth 4.
- Self-play finishes 50-75% of games, contact 21.4 captures/100 plies (blind
  15.8, greedy-material 33.5). The ladder is intact and L2 is the first level
  that plays recognisably.

### Traps hit and fixed
1. `chess.polyglot` needs an explicit import (attribute error, not a name error).
2. Quiescence depth was derived from `board.ply()`, which counts from the game
   start and never advances inside the extension — so the cap was silently
   disabled. Now an explicit `qdepth` parameter, with a regression test that
   records the max depth actually reached.
3. `sorted()` on `chess.Move` raises TypeError (no ordering). Compare `.uci()`.
4. The whole-suite run timed out at 30 min before the above were fixed; the
   match-based tests are the slow part (~34s of the suite) and the default 120s
   bash timeout will not cover the full suite. Use a longer timeout or
   `-k` to select.

## L3 complete: the board-reading perceptron

New module `src/chessrl/perceptron.py` (`PerceptronScorer`, `L3Policy`,
`L3Trainer`, `PerceptronConfig`, `L3Config`), new test file
`tests/test_perceptron.py` (63 tests). **394 tests passing, 53s.**

### Shape of the model, and why

The obvious design -- flatten `(26, 8, 8)` and multiply by a weight matrix --
needs 6.8M parameters for the destination head alone. That is a lookup table,
not a perceptron, and it would never converge here. So L3 stays **factorised**
like L1 but each factor becomes a small perceptron over *local* features:

- origin head `W_from (64, n_ch)` -- score a square from its own channels
- destination head, three additive sub-terms: `W_to_dst (64, n_ch)` (dest's own
  channels), `W_to_src (64, n_ch)` (origin's channels, broadcast to all dests),
  `W_geom (64, 9)` (origin->destination geometry)
- a 32-unit ReLU context pathway (`W_ctx`, `W_hid`) fed by the 9 global scalars,
  because "a knight on the rim is bad" is a *conjunction* a purely linear model
  cannot express
- a tiny 5-slot promotion head

**7225 parameters total.** The einsum form is load-bearing:
`np.einsum("sc,cs->s", W, chan)` contracts the *channel* axis only. Writing
`W @ chan` is the natural mistake and it is wrong in a way that still runs --
it produces a `(64, 64)` every-square-against-every-square table that only
fails several calls later.

### The headline bug: square-indexed weights need the canonical frame

**The heads were reading geometry in absolute board coordinates.** `encode(...,
canonicalise=True)` reflects the ranks for Black, so in the tensor the side to
move always has its pawns on rank 1 and "forward" means "increasing rank" for
*both* colours. But the policy hands the heads **raw** squares (it must -- it
returns a real `chess.Move`), and the heads were computing `(tr - fr)` and
`tr / 7` on those raw squares. So a pawn push e1->e2 and its mirror e8->e7, which
are the same canonical move, produced opposite geometry features.

Caught by mirroring `r3k2r/Pppp1ppp/1b3nbN/nP6/BBP1P3/q4N2/Pp1P2PP/R2Q1RK1` and
finding a **6.1e-03** probability difference where there should be none. After
the fix: **1.5e-08** (float32 accumulation). A 400,000x improvement, and the
residual is no longer a real asymmetry.

The fix is a per-position `_canon_sq` map (identity for White, rank reflection
for Black) applied in *four* places that must agree: `from_logits` (scatter
canonical logits back to real squares), `to_logits`, `_move_features`, and --
critically -- `L3Trainer.apply_credit`. **Training and inference must address the
same weight row.** If inference read `W_from[canonical]` while training nudged
`W_from[real]`, Black's moves would update rows nobody reads and the model would
train only on White's games. Test `test_credit_for_black_updates_a_row_that_
inference_reads` exists specifically for that.

### Second real bug: the seed never reached the scorer

`L3Policy.__init__` did `scorer or PerceptronScorer()`, which builds the scorer
with the **default seed 0** and forwards `seed` only to the policy's *sampling*
RNG. So every `L3Policy(seed=n)` started from identical weights -- "seeded and
reproducible" silently meant "every run is the same run". Both RNGs need the
seed; there are two separate objects. Test: `test_different_seeds_give_
different_weights`.

### Third real bug: `load` hardcoded a BlindScorer

`FactoredSoftmaxPolicy.load` builds `BlindScorer()` unconditionally, which is
right for L1 and wrong for L3 -- it would rebuild a position-blind L3 or fail on
a missing key. Overridden as a `classmethod` on `L3Policy` rather than putting
L3 knowledge into the L1 module.

### What L3 does *not* claim

A freshly initialised L3 does **not** beat blind L1. Measured over 6 games:
**all six are draws by fivefold repetition, zero decisive.** Board *inputs* plus
random *weights* is no more chess knowledge than L1 until it is trained. The
first version of that test asserted "L3 beats L1" and failed 0-6; the honest
test asserts the games terminate and that an untrained L3 wins nothing, and a
separate test verifies the *training mechanism* (a trained model prefers a free
capture it previously ignored, and then plays it greedily).

### Test-position trap worth remembering

I picked `3qk3/8/8/8/8/8/8/3QK3` as "a free queen for White" and it is not:
`Qxd8 Kxd8` is a queen trade and the honest value is 0. The engine was right and
my test was wrong. Use `k2q4/8/8/8/8/8/8/3R3K` -- `Rxd8` scores 501 vs -395 for
the alternatives, a ~900cp gap, and no recapture exists. **Verify a "clearly
best move" position with the engine before asserting the engine finds it.**

### Other test bugs found (all mine, none in the library)
- "Offers" in `ProbCounter.stats()` count distinct *origins* (10 from the
  opening array), not legal moves (20). Same trap as L1.
- Credit curve direction: `decay ** plies_from_end` means the **last** ply gets
  weight 1.0 and the first ply the smallest. Asserting `weights[0] > weights[-1]`
  is backwards.

### Status
- L0-L3 complete. 394 tests, 53s. L3: 7225 params, 1.8ms/position,
  symmetry exact to 1.5e-08.
- **L4 (torch, with a parity test against L3) is next.**

## L4 (torch) and L5 (torch-guided alpha-beta)

### L4: parity with L3 is the whole point
`torch_model.py` reimplements L3's scored exactly. `test_logits_match_l3_exactly`
and `test_move_distributions_match_l3_exactly` (diff literally 0.0) are what
justify the rewrite; without them "L4 works" would only mean "L3 is
self-consistent". 38 tests. Key pieces: `torch_masked_softmax` is a required
twin of the numpy one because the numpy version detaches the graph (training
failed with "element 0 does not require grad" until this existed), and
`TorchScorerAdapter` is a real wrapper object -- handing the nn.Module directly
to the policy meant `self.scorer.from_logits(board)` hit the *module's* tensor
signature.

### L5: three real bugs, all invisible at the default settings

**1. Thread count (the big one).** `torch` defaults to one OpenMP thread per
core. For L5's tensors -- one position against a `(64, n_ch, trunk)` weight, a
few tens of thousands of multiply-adds -- the fork/join cost exceeds the
arithmetic. Measured: one leaf's trunk projection 785us at 8 threads vs 471us at
1. Batched at B=64 the ratio inverts and bmm wins 5:1, which is why
`trunk_features` keeps the *mul-sum* spelling for the batch-1 search and the
comment there records all four measured variants. Fix is `GuidedEngine`
`.single_threaded()`, a context manager around `select` -- **not** in
`__init__`, because the thread count is process-global and a trainer in the
same process does benefit from parallelism.
   Effect: depth-3 middlegame **55.3s -> 5.9s**, opening 4.3s -> 0.5s.

**2. The ordering prior was all zeros for Black.** `_model_prior` built its
masks from the *real* board but read head outputs that are in *canonical*
coordinates (the trunk is fed canonically). For White `canon` is the identity so
it is invisible; for Black the mask admits raw squares while the logits are
nonzero at reflected ones. Symptom: `sum(prior.values()) == 0.0` for every
Black-to-move position -- half of every game had a dead prior. Fix: permute the
move mask into canonical coordinates (`mask[canon][:, canon]`) and read every
probability at canonical squares. One frame throughout; do not scatter one
quantity and not the other. `train_on_search_feedback` had the same bug.

**3. `decision_logits` / `destination_logits` were shape-legal only when
`trunk == 64`.** `dec_from.unsqueeze(0)` puts the singleton on the *trunk* axis
and the trailing 1 on the *square* axis, which broadcasts only because the
default trunk width equals the square count -- and then contracts the wrong
axis. `destination_logits` built its gather index as `(B, 64, 1)` instead of
`(B, 1, trunk)`, so `.squeeze(-1)` kept the square axis and the "origin" term
became a sum over all 64 destination rows. At `trunk=32` both raise. The test
that caught this is `test_heads_work_at_trunk_widths_other_than_64` -- **a width
sweep removes the coincidence a shape bug hides behind.**

### L5 measured after the fixes
- 95083 params (trunk=64). Depth-3 middlegame: 3433 nodes, 1.09s (was 19178
  nodes / 55.3s). Depth-4 opening: 1.95s. Depth-5 opening: 22.6s.
- Untrained L5 does not beat L2 -- same reason untrained L3 does not beat L1.
  What is tested is the mechanism: value / prior ablations change the value and
  the node count respectively, and a learned value can never outrank a real
  mate (`_mate_floor = 9000` vs `MATE_SCORE = 100000`; back-rank mates still
  found at depth 2).
- `MinimaxEngine._root_with_value` exposes the root *value* alongside the move.
  Needed because "ordering cannot change the value" is not checkable through
  `select` -- two searches can return the same move while disagreeing on value,
  or different moves while agreeing.

- **L6 (ensemble + tournament bench) is next.** Run L5 at depth 2-3 there;
