# 2026-10-02

## chess-rl-bench: project setup and L0 foundation

Built the L0 foundation of `chess-rl-bench`, a benchmark harness for naive RL
approaches to chess. Six levels behind one `Policy` protocol.

### Environment
- `.venv` in repo root. numpy 2.5.3, python-chess 1.11.2, pytest 8.x.
- torch intentionally NOT installed yet; it is an optional extra for L4/L5 only.
- Run tests with `./.venv/Scripts/python.exe -m pytest`.

### Key correction to the original spec
The spec named a "chessboard library" and described an output space of
`(row 8, col 8, piece 5, dir 3-8, size 1-8)`. That space is the vocabulary of
`chessboard` on PyPI (v1.5.4, GPLv2, 2017) -- a CLI solver for *combinatoric
puzzle placements*, not a playable board. It has no move generation, no turns,
no pawns, and raises on any position where pieces attack each other. Confirmed
by reading its source.

Resolution (user confirmed): use **python-chess** as the rules layer and wrap
our own numpy array-board on top. Moves are addressed as
`(from_square, to_square, promotion)` instead of the puzzle tuple.

### Design decisions worth not re-litigating
- **Plane layout**: `(12, 8, 8)` bool for piece planes, array row = rank,
  row 0 = rank 1. Mirrors python-chess square indexing exactly so no flipping
  happens anywhere except at display time.
- **Canonicalisation**: rank reflection + colour-block swap, NOT a 180
  rotation. See below.
- **Move masks factorised as `(64, 64, 5)`**: `[from, to, promo_slot]` with slot
  0 = not-a-promotion and slots 1-4 = N/B/R/Q. Flat action index is
  `(from*64 + to)*5 + slot` over an ACTION_SPACE of 20480.
- **Value planes** (`capture_value`, `danger_value`, `attack_balance`,
  `own_danger`) are OFF by default in `encode()`. They cost ~40x the binary
  planes. Turn on for L2 and inference, off for corpus building.
- **Channel order is load-bearing.** L3 weights and L4 checkpoints index by
  channel number, so appending is fine but reordering silently corrupts saved
  models. `CHANNEL_ORDER_VERSION` / `COLOUR_PAIRED_CHANNELS` in encode.py pin it.

### Bugs found and fixed (all had passing-looking output before)
1. **`canonical` used a 180 rotation.** Mapped d8 -> e1 instead of d1, silently
   transposing queenside and kingside. It looked correct on the symmetric
   opening array, which is why it survived the first round of testing. Now a
   rank reflection (`flip_ranks`).
2. **`canonical` double-rotated the colour blocks** during in-place assignment.
   Now builds the output in one pass with `np.empty_like`.
3. **Value planes were reflected unconditionally.** White-to-move positions had
   their value planes flipped -- the majority of any corpus, so it did not look
   like a bug. Guard is now `canonicalise and board.turn != chess.WHITE`.
4. **Promotion slot overflow.** `PROMO_SLOT[QUEEN]` was 4 in an axis of size 4.
   `NUM_PROMO` is 5 (sentinel + 4 pieces).
5. **King piece-square table not rank-mirrored for Black.** Start position
   evaluated to +50 instead of 0, biasing every search towards White. The king
   is in a separate branch from the other tables, which is how it was missed.
6. **`MidstateStore.sample` over-delivered and could duplicate.** Now samples
   without replacement, capped at `min(n, len(entries))`.
7. `hit_rate`/corpus JSON round-trip `material_ratio` was rounded to 4 places,
   shifting entries across the phase boundary on reload. Now full precision.

### Testing infrastructure that earned its keep
`tests/conftest.py::colour_mirror` is the highest-value helper in the repo. It
swaps colours and reflects ranks, carrying castling rights and the en-passant
target across. Every symmetry bug above was caught by comparing
`encode(position)` against `encode(colour_mirror(position))`. It must stay
correct: an early version dropped castling rights and the en-passant square,
which produced *false* failures that cost real time to diagnose.

## L1 / L1.5 complete: the blind policy, and the finding it produced

New modules: `policy.py` (blind factored softmax + counters),
`train_naive.py` (credit assignment + training loop), `diagnostics.py`.
281 tests passing in 4.9s.

### The L1 headline result, and why it is the benchmark's actual output

**A blind policy under a ply cap cannot learn from win/loss reward.** Measured:
12 self-play games at 60 plies produced 0 decisive results and **0 logit
updates**. After 400 training games, an evaluation match still ended with 55 of
60 games unfinished and the trained policy *losing* the 5 that resolved.

This is not a bug. Verified three ways:
- Random play reaches a decisive/drawn result in only ~1/3 of games at 300
  plies (`reasons: max_plies 13/20`).
- Greedy-material (a *seeing* policy) finishes 100% of games with ~2.5x the
  capture contact rate. The diagnostic can tell the two apart, so it is
  measuring something real.
- Blind play makes contact (`Qxh5+` appears in ordinary games) but essentially
  never delivers mate.

The consequence for the build: **L1 needs shaped reward to train at all.**
`TrainConfig.shaped_reward` (default on) scores an unfinished game by the
static evaluation of its final position instead of discarding it. Same 12
games: **2160 updates with shaping, 0 without.** That is the whole difference.

Two more structural fixes fell out of this:

1. **Self-play against the same live object is degenerate.** Both sides make
   identical decisions, so a symmetric position mirrors itself and one side
   cannot be better than the other. `FactoredSoftmaxTrainer._opponent()` now
   deep-copies a *frozen* snapshot as the opponent, refreshed every 10 games,
   with its own RNG stream. Colours alternate each game so no first-move bias
   is learned.
2. `FactoredSoftmaxTrainer(TrainConfig(...))` now works — passing only a config
   used to be silently treated as the policy and fail far from the call site.

### A property of factorised softmax worth remembering

A factored softmax with zero logits is uniform **per factor**, not uniform over
the move set. `P(from) * P(to|from) * P(promo)` means each origin spreads its
own mass over its own destinations, so a square with more legal moves gives each
of its moves less probability. `uniformity == 1.0` holds *only* when every origin
has the same destination count — true in the opening (ten origins x 2 dests) and
in symmetric middlegames, false otherwise (0.881 and 0.808 on two probe FENs).
Never above 1.0. Documented in `policy_sharpness`.

### Test-suite correction
`test_play_game_reaches_a_real_result` asserted random play always finishes
within 300 plies. That was false in general and became actively wrong once the
expensive claimable-draw scan was removed from `is_game_over` for the 17.6x
speedup (e.g. threefold-repetition games now correctly run to the cap). Split
into `test_play_game_always_terminates_with_a_reported_reason` (asserts a valid
reason, not a finished game) and `test_random_play_finishes_for_at_least_some_games`.

## L2 complete: alpha-beta search and the non-learning wrapper

New module `src/chessrl/search.py`: `MinimaxEngine`, `MinimaxPolicy`,
`InformedMinimaxPolicy`, plus `score_move` / `order_moves`.
New test file `tests/test_search.py` (48 tests). **331 tests passing, 102s.**

### What L2 is made of
Negamax + alpha-beta, MVV-LVA ordering, zobrist transposition table, iterative
deepening, quiescence with stand-pat. `chess.polyglot` must be imported
explicitly — `import chess` alone does not expose `chess.polyglot.zobrist_hash`,
which is how cache.py does it too.

Node counts at depth 4 from the opening, as an ablation:
full **2049**, no-TT 3254 (the TT saves 37%), no-iterative-deepening 2665,
no-quiescence 2059. Quiescence is node-neutral here; it exists for correctness
against the horizon effect, not for speed. Worth remembering next time someone
asks whether an optimisation "helped" — the TT and ID clearly did, quiescence
did not, and conflating the three would have hidden that.

### The claim I had to correct
I first documented the wrapper as "cannot change the returned move". That is
**false** and the test caught it. Correct statement: ordering cannot change the
*value* returned by a correct-window alpha-beta, but it decides which move is
returned when several share that value, because the first move to reach alpha is
kept.

Measured, `.../4pP2/8/8/PPPPP1PP/RNBQKBNR b KQkq f6 0 3`: Nf6 and Nc6 both
evaluate to exactly **90** at depth 3. Plain engine returns Nf6 (board order);
the wrapper returns Nc6 because L1's blind prior weights the b8 origin 0.0385 vs
0.0256. It resolved a tie on no chess grounds — which is exactly and only what a
blind prior can legitimately do. Tests now assert the value invariant plus "any
disagreement must be a genuine tie", which is the honest and still-strong
property.

### L2 measured strength
- **Wins 100% against every lower level** — L1 blind, random, greedy-material —
  18/18 across three matches, all decisive, zero unfinished.
- Deeper beats shallower: d2 beats d1 (2-0), d3 beats d2 (2-0, 2 draws).
- Finds Qxf7#, Qh4# and back-rank mates at depth 2, in 0.14s at depth 4.
- Self-play finishes 50-75% of games, contact 21.4 captures/100 plies (blind
  15.8, greedy-material 33.5). The ladder is intact and L2 is the first level
  that plays recognisably.

### Traps hit and fixed
1. `chess.polyglot` needs an explicit import (attribute error, not a name error).
2. Quiescence depth was derived from `board.ply()`, which counts from the game
   start and never advances inside the extension — so the cap was silently
   disabled. Now an explicit `qdepth` parameter, with a regression test that
   records the max depth actually reached.
3. `sorted()` on `chess.Move` raises TypeError (no ordering). Compare `.uci()`.
4. The whole-suite run timed out at 30 min before the above were fixed; the
   match-based tests are the slow part (~34s of the suite) and the default 120s
   bash timeout will not cover the full suite. Use a longer timeout or
   `-k` to select.

## L3 complete: the board-reading perceptron

New module `src/chessrl/perceptron.py` (`PerceptronScorer`, `L3Policy`,
`L3Trainer`, `PerceptronConfig`, `L3Config`), new test file
`tests/test_perceptron.py` (63 tests). **394 tests passing, 53s.**

### Shape of the model, and why

The obvious design -- flatten `(26, 8, 8)` and multiply by a weight matrix --
needs 6.8M parameters for the destination head alone. That is a lookup table,
not a perceptron, and it would never converge here. So L3 stays **factorised**
like L1 but each factor becomes a small perceptron over *local* features:

- origin head `W_from (64, n_ch)` -- score a square from its own channels
- destination head, three additive sub-terms: `W_to_dst (64, n_ch)` (dest's own
  channels), `W_to_src (64, n_ch)` (origin's channels, broadcast to all dests),
  `W_geom (64, 9)` (origin->destination geometry)
- a 32-unit ReLU context pathway (`W_ctx`, `W_hid`) fed by the 9 global scalars,
  because "a knight on the rim is bad" is a *conjunction* a purely linear model
  cannot express
- a tiny 5-slot promotion head

**7225 parameters total.** The einsum form is load-bearing:
`np.einsum("sc,cs->s", W, chan)` contracts the *channel* axis only. Writing
`W @ chan` is the natural mistake and it is wrong in a way that still runs --
it produces a `(64, 64)` every-square-against-every-square table that only
fails several calls later.

### The headline bug: square-indexed weights need the canonical frame

**The heads were reading geometry in absolute board coordinates.** `encode(...,
canonicalise=True)` reflects the ranks for Black, so in the tensor the side to
move always has its pawns on rank 1 and "forward" means "increasing rank" for
*both* colours. But the policy hands the heads **raw** squares (it must -- it
returns a real `chess.Move`), and the heads were computing `(tr - fr)` and
`tr / 7` on those raw squares. So a pawn push e1->e2 and its mirror e8->e7, which
are the same canonical move, produced opposite geometry features.

Caught by mirroring `r3k2r/Pppp1ppp/1b3nbN/nP6/BBP1P3/q4N2/Pp1P2PP/R2Q1RK1` and
finding a **6.1e-03** probability difference where there should be none. After
the fix: **1.5e-08** (float32 accumulation). A 400,000x improvement, and the
residual is no longer a real asymmetry.

The fix is a per-position `_canon_sq` map (identity for White, rank reflection
for Black) applied in *four* places that must agree: `from_logits` (scatter
canonical logits back to real squares), `to_logits`, `_move_features`, and --
critically -- `L3Trainer.apply_credit`. **Training and inference must address the
same weight row.** If inference read `W_from[canonical]` while training nudged
`W_from[real]`, Black's moves would update rows nobody reads and the model would
train only on White's games. Test `test_credit_for_black_updates_a_row_that_
inference_reads` exists specifically for that.

### Second real bug: the seed never reached the scorer

`L3Policy.__init__` did `scorer or PerceptronScorer()`, which builds the scorer
with the **default seed 0** and forwards `seed` only to the policy's *sampling*
RNG. So every `L3Policy(seed=n)` started from identical weights -- "seeded and
reproducible" silently meant "every run is the same run". Both RNGs need the
seed; there are two separate objects. Test: `test_different_seeds_give_
different_weights`.

### Third real bug: `load` hardcoded a BlindScorer

`FactoredSoftmaxPolicy.load` builds `BlindScorer()` unconditionally, which is
right for L1 and wrong for L3 -- it would rebuild a position-blind L3 or fail on
a missing key. Overridden as a `classmethod` on `L3Policy` rather than putting
L3 knowledge into the L1 module.

### What L3 does *not* claim

A freshly initialised L3 does **not** beat blind L1. Measured over 6 games:
**all six are draws by fivefold repetition, zero decisive.** Board *inputs* plus
random *weights* is no more chess knowledge than L1 until it is trained. The
first version of that test asserted "L3 beats L1" and failed 0-6; the honest
test asserts the games terminate and that an untrained L3 wins nothing, and a
separate test verifies the *training mechanism* (a trained model prefers a free
capture it previously ignored, and then plays it greedily).

### Test-position trap worth remembering

I picked `3qk3/8/8/8/8/8/8/3QK3` as "a free queen for White" and it is not:
`Qxd8 Kxd8` is a queen trade and the honest value is 0. The engine was right and
my test was wrong. Use `k2q4/8/8/8/8/8/8/3R3K` -- `Rxd8` scores 501 vs -395 for
the alternatives, a ~900cp gap, and no recapture exists. **Verify a "clearly
best move" position with the engine before asserting the engine finds it.**

### Other test bugs found (all mine, none in the library)
- "Offers" in `ProbCounter.stats()` count distinct *origins* (10 from the
  opening array), not legal moves (20). Same trap as L1.
- Credit curve direction: `decay ** plies_from_end` means the **last** ply gets
  weight 1.0 and the first ply the smallest. Asserting `weights[0] > weights[-1]`
  is backwards.

### Status
- L0-L3 complete. 394 tests, 53s. L3: 7225 params, 1.8ms/position,
  symmetry exact to 1.5e-08.
- **L4 (torch, with a parity test against L3) is next.**

## L4 (torch) and L5 (torch-guided alpha-beta)

### L4: parity with L3 is the whole point
`torch_model.py` reimplements L3's scored exactly. `test_logits_match_l3_exactly`
and `test_move_distributions_match_l3_exactly` (diff literally 0.0) are what
justify the rewrite; without them "L4 works" would only mean "L3 is
self-consistent". 38 tests. Key pieces: `torch_masked_softmax` is a required
twin of the numpy one because the numpy version detaches the graph (training
failed with "element 0 does not require grad" until this existed), and
`TorchScorerAdapter` is a real wrapper object -- handing the nn.Module directly
to the policy meant `self.scorer.from_logits(board)` hit the *module's* tensor
signature.

### L5: three real bugs, all invisible at the default settings

**1. Thread count (the big one).** `torch` defaults to one OpenMP thread per
core. For L5's tensors -- one position against a `(64, n_ch, trunk)` weight, a
few tens of thousands of multiply-adds -- the fork/join cost exceeds the
arithmetic. Measured: one leaf's trunk projection 785us at 8 threads vs 471us at
1. Batched at B=64 the ratio inverts and bmm wins 5:1, which is why
`trunk_features` keeps the *mul-sum* spelling for the batch-1 search and the
comment there records all four measured variants. Fix is `GuidedEngine`
`.single_threaded()`, a context manager around `select` -- **not** in
`__init__`, because the thread count is process-global and a trainer in the
same process does benefit from parallelism.
   Effect: depth-3 middlegame **55.3s -> 5.9s**, opening 4.3s -> 0.5s.

**2. The ordering prior was all zeros for Black.** `_model_prior` built its
masks from the *real* board but read head outputs that are in *canonical*
coordinates (the trunk is fed canonically). For White `canon` is the identity so
it is invisible; for Black the mask admits raw squares while the logits are
nonzero at reflected ones. Symptom: `sum(prior.values()) == 0.0` for every
Black-to-move position -- half of every game had a dead prior. Fix: permute the
move mask into canonical coordinates (`mask[canon][:, canon]`) and read every
probability at canonical squares. One frame throughout; do not scatter one
quantity and not the other. `train_on_search_feedback` had the same bug.

**3. `decision_logits` / `destination_logits` were shape-legal only when
`trunk == 64`.** `dec_from.unsqueeze(0)` puts the singleton on the *trunk* axis
and the trailing 1 on the *square* axis, which broadcasts only because the
default trunk width equals the square count -- and then contracts the wrong
axis. `destination_logits` built its gather index as `(B, 64, 1)` instead of
`(B, 1, trunk)`, so `.squeeze(-1)` kept the square axis and the "origin" term
became a sum over all 64 destination rows. At `trunk=32` both raise. The test
that caught this is `test_heads_work_at_trunk_widths_other_than_64` -- **a width
sweep removes the coincidence a shape bug hides behind.**

### L5 measured after the fixes
- 95083 params (trunk=64). Depth-3 middlegame: 3433 nodes, 1.09s (was 19178
  nodes / 55.3s). Depth-4 opening: 1.95s. Depth-5 opening: 22.6s.
- Untrained L5 does not beat L2 -- same reason untrained L3 does not beat L1.
  What is tested is the mechanism: value / prior ablations change the value and
  the node count respectively, and a learned value can never outrank a real
  mate (`_mate_floor = 9000` vs `MATE_SCORE = 100000`; back-rank mates still
  found at depth 2).
- `MinimaxEngine._root_with_value` exposes the root *value* alongside the move.
  Needed because "ordering cannot change the value" is not checkable through
  `select` -- two searches can return the same move while disagreeing on value,
  or different moves while agreeing.

- L0-L5 complete. **460 tests, 3m30s** (the L4/L5 torch tests dominate).
- **L6 (ensemble + tournament bench) is next.** Run L5 at depth 2-3 there;

## bench/ : the round-robin scoreboard (Task #8 complete)

Built the scoreboard package. Files: `bench/levels.py` (roster + opening book),
`bench/runner.py` (match loop), `bench/rating.py` (Bradley-Terry fit),
`bench/report.py` (ASCII tables), `bench/__main__.py` (CLI), `bench/README.md`.

### The rating fit: four consecutive scale bugs, all "converged, correct-looking, wrong"

This cost most of the session and the lesson is worth keeping verbatim:

1. **Units error (the big one).** Optimised Elo points with an `r**2` prior.
   At any real rating gap the prior was ~10^4x stronger than the likelihood
   (penalty 2500 at a 100-point gap vs ~2 of evidence from 3 games), so *every*
   entrant fitted to 0.0. Fix: optimise the **logistic parameter**
   `theta = r * ln(10)/400`, where the count-weighted gradient is `n*(1-p)` --
   order 1 per game -- and a unit-variance prior is commensurate. Convert to Elo
   only at the end (`r = theta / c`). Elo scale `c` then appears in exactly two
   places: the rating->probability sigmoid, and the final division.
2. **Prior deleted by re-centring the ratings each iteration.** Re-centring a
   mean-zero prior gradient is a no-op *on it*, so the prior's contribution
   vanished and a 10-0 sweep "converged" to 3127 Elo. Fix: project the *step*
   into the sum-zero subspace, never re-centre the parameters.
3. **Projecting the Hessian into the sum-zero subspace** to fix the gauge
   deleted the prior diagonal, leaving `[[w,-w],[-w,w]]` -- singular. The solve
   raised `LinAlgError`, my `except` fell back to the raw gradient, and Newton
   silently became badly-scaled descent. The prior *is* what identifies the
   level; do not project it away. Fallback is now `pinv`, never the raw
   gradient (a gradient is a direction, not a step).
4. **A count is not a probability.** Each observation is `n` games that came out
   the same way, so the term is `n * log(p)`; its derivative is `n*(1-p)` and the
   Hessian `n*p*(1-p)` -- **both carry the count**. Writing `(ss - p)` is right
   for one game and wrong for a count, so it passes any test that only plays
   single games. Caught only by checking the likelihood at the fitted point vs
   a grid maximum.

Solver is now **damped Newton** (concave objective -> globally convergent, no
step size to tune). Converges in 5-9 iterations. Verified against an independent
bisection oracle to within 0.004 Elo across sweeps of 3..500 games:
3 -> +225, 6 -> +306, 10 -> +370, 20 -> +460, 100 -> +680, 500 -> +911 Elo.
`tests/test_rating.py` asserts these analytic values, not "it converged" --
because every one of the four bugs above converged.

### Two real runner bugs, both invisible without a test

- **Opening book was not White-to-move.** Half the entries had Black to move.
  `play_game` dispatches by `board.turn`, so the *position* decided who opened
  and the colour assignment was silently inverted -- "A plays White in games 0
  and 2" was false, making an even-looking match colour-biased. Rewrote the book
  to 6 distinct White-to-move positions (Italian, QGD, Indian, Sicilian, English)
  and added `assert_white_to_move` + a test that watches which policy actually
  makes the first move. Now `['A','B','A','B']`.
- **`book[i // 2]`** used one opening per *pair* of games, so a 6-game match from
  a 6-entry book used 3 distinct positions twice each. Per game now: `book[i]`.
- `build()` replaced a torch ImportError's message with just `"unavailable:
  ImportError"`, losing the module name. Now keeps it.
- Report contained `±`/`Δ`/`…` -- the "plain ASCII" claim in its own docstring
  was false. All ASCII now.
- `format_summary` derived the game total from `len(m.games)`, which a JSON
  round-trip drops, so a reloaded report printed "0 games (108 decided)". Now
  counts `played + unfinished` from the records.

Wrote `specs/L3.5-squarelocal.md` (design only, no code; **retired 2026-10-02**
after implementation — findings moved to `bench/README.md` and HYPOTHESES.md).
Motivation from a
discussion about comparing paradigms: the ladder varies *how much* information a
learner gets (blind L1 -> informed L3) and *depth vs linear* (L3 -> L4) but never
**the shape of the computation** at fixed input/output/budget. L3.5 is that rung.

Core mechanism: `PerceptronScorer.from_logits` already does
`einsum("sc,cs->s", W_from, chan)` with a **separate weight row per square**
`(64, n_ch)`. L3.5 replaces it with `(n_ch,)` applied at all 64 squares — a 1x1
conv / weight-tied layer. 64x fewer params in the square-local path. Named
"squarelocal" (not "CNN") deliberately: the tied linear layer is the weakest
structurally-aware thing that is still tied.

Falsifiable claims (both stated in the spec so a negative is a result):
1. A single shared function per square is sufficient — false if square value
   depends irreducibly on global structure (open file, "a fact about seven other
   squares").
2. Pair-relative geometry is enough to carry origin/destination asymmetry —
   since tying removes L3's `W_to_src` per-origin row. Must be tested by
   `test_origin_dependence_survives_tying`.

Key spec decisions:
- **Equal-budget constraint is load-bearing.** L3 is 7225 params
  (`test_parameter_count_is_in_the_low_thousands`). L3.5 must land within +/-10%
  or the comparison is meaningless. Budget knob is `h_ctx` (context hidden
  width), since the square-local heads collapse. Asserted as a test, not just
  documented.
- **The divergence trap.** A tied row gets an update for every square per ply, so
  it moves ~64x faster than L3's per-square rows and diverges at L3's `lr=0.01`.
  Fix per spec: separate `lr_shared` defaulting to `lr/64`, plus a test that
  weights stay bounded — the failure is otherwise silent.
- **Three-arm experiment.** L3 (incumbent) / L3.5 (tied) / L3-flat (flat MLP over
  `encode()`, the control expected to underperform). Without the control a win is
  indistinguishable from "any change from L3 helps". All at <=10% param spread.
- New file `src/chessrl/squarelocal.py`, deliberately NOT added to
  `perceptron.py` so L3 can be deleted independently.
- Reuses `set_position` / `_canon_sq` / `_to_real` verbatim; the frame machinery
  is untouched. Weight tying is only coherent *because* the encoder canonicalises.
- Non-goal restated: the neuro-symbolic planner cannot live on this ladder,
  because it chooses its own feature space and so cannot be ablated against L3.

### H23 — special moves: legal, but underplayed (tested)

User asked whether the computer player can castle, en-passant, etc. Tested rather
than asserted. Added H23 to `HYPOTHESES.md` and recorded the finding in
`MEMORY.md` under "Known traps".

  `board.legal_moves`, so it admits 100% of legal moves — verified `O-O`/`O-O-O`
  on `r3k2r/8/8/8/8/8/8/R3K2R w KQkq`, ep on the f6 position, and all four

  passant: 2 total across all L1/L3 games; 0 for material/random/L2-d2. Searching
  levels castle because they have a reason; blind/untrained ones do not.
- **Isolated the cause (two concrete findings):**
  1. `value.evaluate()` is `material_value + piece_square_score` and nothing
     else — **no castling term, no en-passant term, no mobility term**. Castling
     pays only incidentally through the king PST; rook connectivity, pawn shield
     and tempo cost are invisible. En passant is invisible beyond the immediate
     pawn capture.
  2. **No castling-rights channel in the encoder.** `CHANNELS` has 22 binary
     planes, none for castling rights; ep is 21, promotion ranks 19/20.
     `has_castling_rights` exists only as one scalar in `board_context_features`.
     A learner therefore cannot express "I may still castle kingside" as a board
     pattern — the exact information needed to decide whether to castle.
- **Verified NOT bugs (checked because they were the likely suspects):** the ep
  plane canonicalises correctly (black-to-move f6 -> plane f3 after rank
  reflection, matching `colour_mirror`; `encode(pos)` vs `encode(mirror(pos))`
  max abs diff **exactly 0.0**). Promotion slots have no queen bias — uniform
  promo logits give 0.25 each over N/B/R/Q, so under-promotion is not
  structurally suppressed, just unlikely.
- Not fixed — this is a finding, not a patch. Any fix must append channels
  (append-only rule) and, if castling is to be *preferred*, add an eval term.

## L3.5 — the weight-tied per-square scorer (implemented)

Implemented the L3.5 design doc. New module `src/chessrl/squarelocal.py`,
tests `tests/test_squarelocal.py` (73 tests), roster arms in `bench/levels.py`.

### What it is
Deletes per-square indexing from L3's square-local heads:
`einsum("sc,cs->s", W_from, chan)` -> `einsum("c,cs->s", w_shared, chan)`.
A 1x1 convolution / weight-tied linear layer over the square axis. It is a
`Scorer`, not a policy, so `FactoredSoftmaxPolicy` masking/sampling/game loop are
inherited unchanged.

### Final layout (783 params, 1/9.23 of L3's 7225)
`w_shared 22 | b_shared 1 | W_ctx 576 | w_hid 64 | w_dst_shared 22 |
w_dst_ctx 64 | w_geom 9 | promo 25`. `h_ctx=64` (`LEAN_H_CTX`) is the only knob.

### Two findings that would have silently wrecked the experiment
1. **`lr_shared = lr/64` alone disables the tied heads.** At `lr=0.05`,
   `credit=0.5`, the step is `1024 * 0.05/64 * 0.5 = 0.4` grid units -> rounds to
   0. Measured: 30 games / 14,400 updates left `w_shared`, `b_shared`,
   `w_dst_shared`, `w_geom`, `promo` **bit-identical to init**; only `W_ctx`
   (full lr) moved. Fix: **error feedback** — a per-tensor `_residual` buffer
   banks sub-grid remainders (`~2.5` events of 0.4 units = one real step). All
   eight tensors move after the fix.
2. **Context path MUST NOT be normalised.** `W_ctx` is a single shared
   `(h_ctx, 9)` at both levels; dividing it too would handicap the only pathway
   the tying hypothesis can survive on. Measured relative drift: `W_ctx` 59.2
   (L3) vs 61.6 (L3.5) — matched, as intended.

### Spec's second falsifiable claim is partly false (§5b in the spec)
`_geom_features` has `dest_rank` but **no destination-file term**, and uses
`abs(tf-ff)`. So `b1->c3` and `g1->h3` give byte-identical geometry vectors, and
two knights have identical channels with an origin-blind tied destination row =>
the model **cannot express "a knight belongs near the centre, not the rim"**.
L3 can, via its per-destination `W_to_dst` row. Reported, not patched: adding a
feature would change the fixed feature set the comparison rests on.

### Tie phenomenon (expected, not a bug)
Tying makes b1/g1 knight origin logits **exactly equal**; L3 breaks that tie only
by per-square init noise. Nc3/Nf3 are genuinely equivalent, so L3.5 is right to
tie. Greedy then falls back to array order, so **L3's
`test_mirrored_positions_select_mirrored_moves_when_greedy` cannot be ported**;
replacement invariant is that *probabilities* mirror exactly (residual 1.49e-08).

### Control arm `L3-flat`
`FlatScorer`/`FlatPolicy` in `squarelocal.py` — one hidden layer over the
flattened `(22,8,8)` tensor, `h_flat=1` (1408 weights for one unit), 1445 params.
Origin head is a **constant** across squares (std 0.0) — that is the spatial
structure it gives up. Colour-symmetric to 1.5e-08.

### Budget deviation (recorded, not hidden)
Spec §3 demands +-10% of L3 (6503..7948) AND its own layout table says 783 —
contradictory. Chose 783 (user-approved "lean, purely tied"). Matching would
need `h_ctx≈649`, a ReLU of width 649 over a **9-dim** input = padding. Arms sit
at 100% / 10.8% / 20.0%. Test asserts both readings so a switch fails loudly.

## L6 ensemble built — and it produced a negative result

Task: "can you make L6 a reality?" There is **no L6 spec** (`specs/` has only
`L3.5-squarelocal.md`), so L6 was implemented from the ladder description plus
requirements scattered in `__init__.py`, `game.py`, `guided.py`, `diagnostics.py`.

### New files
- `src/chessrl/ensemble.py` (~660 lines) — `MemberKind`, `MemberSpec`,
  `MemberAccuracy`, `OutcomeLedger`, `EnsembleConfig`, `EnsemblePolicy`,
  `accuracy_weights`, `score_member_opinions`, `_move_is_safe`.
- `tests/test_ensemble.py` — 90 tests.
- `bench/ensemble_run.py` — calibrate -> fit -> report driver.
- `bench/levels.py` — `_l6` factory + roster entry (needs_torch=False, tag
  "ensemble"); `tests/test_bench.py` — 8 more tests.

### Two-stage combination (the design point)
`EnsemblePolicy` is a `DistributionPolicy` that holds **both kinds of member**:
it *blends* those exposing `move_distribution` (L1, L3) and *votes* those
exposing only `select` (L2-d2). `MemberKind` is **derived** via
`hasattr(policy, "move_distribution")`, never declared — a caller-supplied flag
would let a typo put a single move into a blend as if it were a probability
spread. Output is renormalised **on read**: weights of 1.0 each give total mass
n_members, and the game loop samples without renormalising.

### Three real bugs found
1. `accuracy_weights` had `scaled = acc / chance_equivalent * chance_equivalent`
   — a tautology cancelling to `acc`, making `chance_equivalent` a **dead knob**
   (referenced nowhere else in the repo). Fixed to `w = acc / chance_equivalent`
   (chance == the *unit* of accuracy, so a member at chance = one mean vote =
   an untried member). Documented with the reasoning; the old form is called out
   in the docstring so it is not reintroduced.
2. `bench/ensemble_run.py`: `EnsemblePolicy(config)` positionally binds to
   `members`. Fixed to keyword; comment records why.
3. `OutcomeLedger.load` could not read a ledger embedded in a larger artefact.
   Split out `OutcomeLedger.from_dict`; `load` now delegates.

### THE RESULT: fitted weights make the ensemble worse
Calibration (4 games/pair, 24 positions/game): accuracies L1 0.583, L3 0.625,
L2-d2 0.917 -> weights 0.2745 / 0.2941 / 0.4314. Ordering exactly as the ladder
predicts. **Yet it plays worse.** vs greedy-material:
- fitted weights: unfinished as White (100 plies), checkmate as Black (59)
- L2-d2 all the weight: **checkmate as White in 39** == L2-d2 alone
- L2-d2 alone: checkmate both colours (39 / 40)

Cause: the two blind members hold **0.569** together and outvote the one that
sees material. The fitted ensemble's White opening is `b4 Nc6 d3 Nxb4 Nc3
Nxd3+ Qxd3` — it hangs three pawns for a queen. The accuracy metric does not
punish this because *agreement with the winner's move* is cheap on positions
where one move is obvious. **Agreement is not competence.**

This is a negative result about the *metric*, not about ensembles. Next step:
a metric with a sign for material — `_move_is_safe` is the existing half of
exactly that idea (currently used only for unfinished games). Locked in by
`test_the_fitted_ensemble_is_worse_than_its_best_member`, which asserts the
mechanism (blind majority > search member) rather than the brittle game result.

Status in `ONBOARDING.md`: L6 = "implemented, negative result". Recorded in
`bench/README.md` with the measured table.

## L6 bug hunt — five real bugs found and fixed

"fix bugs" after the L6 build. Reviewed with fresh eyes and **measured** each
suspicion instead of guessing. Five genuine defects, two of which made the
ledger report fake evidence.

### 1. `_move_is_safe` was dead code (worst bug)
Threshold `(after - before) > -100` on a static `evaluate()` swing. `evaluate`
is material+PST only, so it cannot see the opponent's reply and the swing is
just the mover's own material delta. Measured over **11,691 legal moves**: range
was only **−50 … +99957** — the minimum never reached −100, so it returned
`True` for **100%** of moves, incl. 200/200 random. Every unfinished game (the
majority here) gave every member a perfect score. Fixed with a
`recapture_risk`-based test: unsafe when the cheapest enemy attacker is worth
less than the piece now on the target and the move did not already win that
much. Now rejects **11.9%** of random moves.

### 2. Loser-side plies were free hits
`correct = (move != played)` when the side to move was the eventual loser.
Inverts the question — the member is asked *what it would play*, not *whether
the played move was good*. Every ply the loser moved became a guaranteed hit.
Measured: a **purely random** member scored **0.429** on a 7-move decisive game
(chance ≈ 0.05). Both sides are now scored by agreement with the played move;
the same random member scores **0.046**.

### 3. `temperature` crashed then produced NaN
`v ** (1.0/temperature)` raised `OverflowError` at `temperature=1e-9`, and
`temperature > 0` is validated as legal. First fix moved the overflow into
`np.exp` → `inf/inf = nan`. Real fix: max-shifted log-space softmax, with raw
zeros pinned (log 0 = −inf would poison the vector). Now valid and finite from
1e-12 to 1e9, no RuntimeWarning.

### 4 & 5. Two documentation lies
- Class docstring claimed stage 2 also voted *zero-weight distribution*
  members. It never did — stage 2 iterates `self.voters`. Skipping is correct;
  the docstring was wrong.
- Module docstring referenced `OutcomeLedger.weights`, which does not exist
  (it is `accuracy_weights`), and described the old pre-fix weighting rule.
- Also made `set_weights_from_ledger`'s duplicate-name behaviour explicit
  (duplicates share a ledger row, hence a weight — caller error, not fixable).

### Corrected L6 result — still negative, but the metric now works
Calibration 4 games/pair: accuracies were L1 0.583 / L3 0.625 / L2-d2 0.917
(with free hits) → now **L1 0.417 / L3 0.375 / L2-d2 0.750**. The blind members
lost a third of their accuracy and L2-d2's share rose 0.431 → 0.487. **But the
blind pair still holds 0.514**, a majority over the one that can see, so the
fitted ensemble still fails to beat L2-d2 alone (unfinished vs checkmate 39/40).

Control proving the machinery is sound: giving L2-d2 all the weight reproduces
L2-d2 exactly. So the cost is the weighting rule, not the combination. Honest
conclusion is now sharper: **the rule lets a blind majority outvote a seeing
minority** — structural, not a tuning matter.

Note my own tests did **not** catch any of the five bugs; the new regression
tests (`test_a_random_member_scores_at_chance_on_a_decisive_game`,
`test_the_safety_proxy_rejects_some_moves`, the temperature parametrisation,
the oracle/never-match identities) exist so they cannot return. Suite 687 → 707.

## Follow-up audit — the safety proxy's power is phase-dependent

Re-verified the "fix bugs" work end to end: all five fixes present in source, full
suite green (707 → 708 with the new pin below).

**New finding, which refines the README claim rather than contradicting it.** The
documented "rejects 11.9% of random moves" is a *blended* figure and hides a
strong phase dependence. Measured acceptance of `_move_is_safe` over random legal
moves sampled at three depths:

```
opening (0 plies)   1200/1200 accepted   (0.0% rejected)
midgame (20 plies)  1657/1904 accepted  (13.0% rejected)
late    (40 plies)  1545/1833 accepted  (15.7% rejected)
```

So in the opening the fallback still accepts **100%** of moves — nothing is
attackable yet, so `recapture_risk` returns 0 for every destination and the
function collapses back to exactly the always-True behaviour it was written to
replace. It is not the old bug (that was 100% *always*, at every phase), but it
is blind for the first several plies.

**Does it matter in practice?** Partly. In real blind-vs-blind games, which run
long, the fallback does discriminate: move-level safe rate 0.80–0.85 and
positions where *every* move is safe only 8–20% of the time. But compare against
a decisive game, where the agreement branch spreads members over the full 0–1
range (a replayer scores 1.00, a random member ~0.05) while this fallback squeezes
everyone into 0.80–0.85. So unfinished games — the majority of this benchmark's
evidence, and the evidence the "blind majority outvotes the seeing minority"
result rests on — carry **much less signal per position** than decisive ones.
That is the concrete reason the headline result should be trusted less than its
weight suggests.

**Method note / my own error:** my first probe reported "unfinished random
accuracy 1.000 over 400 samples", which looked like the bug had returned. It was
my probe's fault — it scored a single start-position FEN, where 0% rejection is
*correct*. The lesson generalises: a probe that only samples the opening will
make this fallback look dead every time. Fixed the probe, then measured across
the real calibration games.

**Change made:** `bench/README.md` line ~344 now carries the phase table and the
0.80–0.85-vs-0–1 spread, replacing the blended "11.9%" phrasing. Added
`test_the_safety_proxy_is_blind_in_the_opening` to pin the property (accepts all
20 start-position moves, but rejects ≥1 in a developed position), so the
phase-dependence stays a known property rather than a rediscovery. Suite 708, all
passing.

## Structural fix attempted and implemented (opt-in relative weighting)

Continued past the bug hunt: the README's open question was whether the "blind
majority outvotes a seeing minority" failure has a structural fix. It does.

**Re-diagnosed the mechanism precisely first (did NOT trust the summary).** With
the *corrected* weights (L1 0.233, L3 0.269, L2-d2 0.498) the ensemble's opening
argmax IS L2's move (g1f3) and it samples it 51.9% of the time — so the old
"blind majority outvotes / b4 Nc6..." story was from the *buggy* calibration
(blind pair had 0.569). With corrected weights the seeing member is the **largest
single weight** (0.498 > 0.269 > 0.233). The real corrected mechanism is
**mixture dilution**: the ~50% of mass on the two perceptrons is concentrated on
their own preferred moves, which compete with L2's single peak under *sampling*,
so across a full game the noise drags the ensemble below pure L2-d2. Measured:
absolute ensemble loses to L2-d2 both colours (0-1 / 1-0, checkmate 19-26p).

**Fix: `EnsembleConfig.relative=True`** — scale each member's accuracy against the
*set mean* instead of `chance_equivalent`; below-mean members clamp to 0.
Implemented in `accuracy_weights` (new `relative` kwarg + branch) and threaded
through `EnsemblePolicy.set_weights_from_ledger` and `bench/ensemble_run.py`
(`--relative` flag). On the same calibration this gives L1 0.0161 / L3 0.0161 /
